The View Transition API

View transitions animate the change between two states of a page. You update the DOM however you like; the browser takes a snapshot before and after, then animates between them using CSS that you control. They work within a single page and, with one line of CSS, across page navigations too.

JavaScript: wrap any DOM update

function updateTheDOM() {
  // …change the page however you like…
}

if (document.startViewTransition) {
  document.startViewTransition(updateTheDOM);
} else {
  updateTheDOM(); // no support: just update
}

CSS: name elements, then style their animation

/* A unique name gives an element its own
   snapshot, so it can move independently. */
.product-photo {
  view-transition-name: product-photo;
}

/* Customise the animation with pseudo-elements. */
::view-transition-group(product-photo) {
  animation-duration: 0.4s;
}

How a view transition works

A same-document view transition always goes through the same five steps:

  1. You call document.startViewTransition(update). It immediately returns a ViewTransition object. Your update callback hasn't run yet.
  2. The browser captures the old state. It takes a snapshot of every rendered element that has a view-transition-name (the root element is named root by default) and records each one's size and position.
  3. Rendering pauses and your callback runs. The user keeps seeing the old state while your callback changes the DOM. It may be async. When it settles, transition.updateCallbackDone settles too.
  4. The browser captures the new state and builds a tree of pseudo-elements on top of the page. transition.ready fulfils: the animation is about to start.
  5. The animations run. When every animation on the pseudo-elements has finished, the tree is removed, the real page shows through again and transition.finished fulfils.

What the browser animates by default

  • ::view-transition-group(name) animates width, height and transform from the old box to the new one, over 0.25 s. That is what makes an element appear to move and resize.
  • ::view-transition-old(name) fades out while ::view-transition-new(name) fades in. Blending them with mix-blend-mode: plus-lighter keeps the cross-fade from dipping in opacity.
  • The old image is a static screenshot; the new image is a live view of the element, so it keeps updating.
  • A name that exists only in the old state just fades out; one that exists only in the new state fades in.
  • While the transition runs, the pseudo-elements cover the page, so clicks and taps go to the document element rather than to your buttons.

Morphing a thumbnail into a detail view

Give an element in the old state and an element in the new state the same view-transition-name and the browser treats them as one thing: their group animates from the old position and size to the new ones. Here the thumbnail you pick and the large artwork share the name gallery-art, and the two titles share gallery-title. Only one element per name can be rendered at a time, so the grid is hidden while the detail view is showing.

function openArtwork(item) {
  // Mark the thumbnail BEFORE starting the transition, so it already
  // has its name when the browser captures the old state.
  grid.querySelector('.is-active')?.classList.remove('is-active');
  item.classList.add('is-active');

  document.startViewTransition({
    update: () => {
      grid.hidden = true;
      detail.hidden = false;
      fillInDetails(item);
      backButton.focus({ preventScroll: true });
    },
    types: ['gallery'],
  });
}
Demo 3

Adding, removing and reordering items

Each card gets a unique name (fruit-apple, fruit-kiwi…) so the browser can follow it wherever it moves. Cards that exist only in the new state (additions) or only in the old state (removals) get their own enter and exit animations, selected with a shared view-transition-class and the :only-child trick. The list is rebuilt from scratch on every change: view transitions match elements by name, not by DOM identity.

  deck = nextDeck; // update the state straight away…

    What about view-transition-name: match-element? In Chrome 137+, Safari 18.4+ and Firefox 144+ it gives every element an automatic name based on its identity, so you don't need to invent unique names. It only helps when the same DOM node survives the update (it doesn't here, because the list is rebuilt), and it can't be feature-detected: older browsers accept match-element as an ordinary name, so every card would share it and the duplicate names would abort the transition. That's why this demo uses explicit names.

    Demo 4

    Transition types: one carousel, four animations

    Types are labels you attach to a transition: startViewTransition({ update, types: ['slide', 'forwards'] }). While it runs, :active-view-transition-type(slide) matches the root element, so you can pick different CSS for different kinds of change without adding and removing classes yourself. Every transition in this carousel has the type carousel, plus the style you choose and a direction. The direction is turned into a number (--vt-direction) so that a single set of keyframes works both ways.

    Driving the animation from JavaScript: a circular theme reveal

    Once transition.ready fulfils, the pseudo-elements exist and you can animate them with the Web Animations API by passing the pseudoElement option to element.animate(). Here the new theme is revealed through a growing clip-path circle that starts where you clicked (or from the middle of the button if you used the keyboard). The theme button in the header does the same thing.

    Current theme: light. All the colours on this page come from light-dark(), so switching theme is a single change to color-scheme.

    Show the code

    CSS

    /* No cross-fade for this type: keep both snapshots fully opaque. */
html:active-view-transition-type(theme)::view-transition-image-pair(root) {
  isolation: auto;
}
html:active-view-transition-type(theme)::view-transition-old(root),
html:active-view-transition-type(theme)::view-transition-new(root) {
  animation: none;
  mix-blend-mode: normal;
}

    JavaScript

    async function switchTheme(event) {
  // Keyboard "clicks" have no pointer position (event.detail is 0).
  const box = event.currentTarget.getBoundingClientRect();
  const x = event.detail ? event.clientX : box.left + box.width / 2;
  const y = event.detail ? event.clientY : box.top + box.height / 2;
  // The distance to the farthest corner, so the circle covers the viewport.
  const radius = Math.hypot(Math.max(x, innerWidth - x), Math.max(y, innerHeight - y));

  const transition = document.startViewTransition({
    update: () => setTheme(nextTheme),
    types: ['theme'],
  });
  await transition.ready;

  document.documentElement.animate(
    { clipPath: [`circle(0 at ${x}px ${y}px)`, `circle(${radius}px at ${x}px ${y}px)`] },
    { duration: 600, easing: 'ease-in-out', pseudoElement: '::view-transition-new(root)' },
  );
}

    The ViewTransition object: promises, skipping and errors

    Each scenario below starts a real transition and logs what happens, with timings, to its three promises. They are the best way to sequence work around a transition, and they show what goes wrong when a transition can't run. A transition that fails is skipped: the DOM still updates, just without the animation.

    The three promises on every ViewTransition.
    PromiseFulfils when…Rejects when…
    updateCallbackDoneyour update callback (or the promise it returns) has finished.the callback throws or its promise rejects.
    readythe pseudo-elements exist and the animation is about to start.the transition is skipped before it can animate: skipTransition(), another transition starting, duplicate names, a slow update timing out, or a failing callback.

    Show the code 
    const transition = document.startViewTransition(update);

transition.updateCallbackDone.then(() => {
  // The DOM is updated. Safe to do follow-up work that doesn't care about the animation.
});

transition.ready
  .then(() => {
    // The pseudo-elements exist: a good moment for element.animate({ … }, { pseudoElement }).
  })
  .catch((error) => {
    // The transition was skipped before animating. The DOM still updates, so
    // this is usually not worth reporting. Without a handler, though, it shows
    // up as an "Uncaught (in promise)" error.
    console.debug('No animation:', error.name);
  });

await transition.finished; // the animation is over; the real page is visible again

// Jump straight to the end (the update callback still runs):
transition.skipTransition();

// Experimental: keep the pseudo-elements alive until a promise settles.
transition.waitUntil(somePromise);

    Element-scoped view transitions

    Experimental: element.startViewTransition() comes from the CSS View Transitions Level 2 draft and is only supported in Chrome and Edge 147+ at the time of writing. In other browsers, the cards below still flip, just instantly.

    Calling startViewTransition() on an element instead of on document scopes the transition to that element's subtree. The element plays the part of the root, its pseudo-element tree hangs off it (.flashcard::view-transition-old(root)), and the rest of the page isn't captured at all. Unlike document-level transitions, where starting a new transition skips the current one, several scoped transitions can run at the same time.

    Multi-page sites

    Cross-document view transitions

    Everything above happens inside one document. Cross-document view transitions animate an ordinary navigation from one page to another page on the same origin, with no JavaScript required. Both pages opt in with CSS. Wrapping the rule in a media query is an easy way to respect reduced motion:

    @media (prefers-reduced-motion: no-preference) {
  @view-transition {
    navigation: auto;
  }
}

    The naming and styling rules are the same as before. Give a thumbnail on one page and the hero image on the next page the same view-transition-name, and it morphs across the navigation.

    Try it: open the planets demo. It has an overview page and four planet pages, with planets that morph between pages, a header that stays put, and different animations chosen with types.

    When does a cross-document transition run?

    • Both the old and the new page must opt in with @view-transition { navigation: auto; }. This guide doesn't, so the link above won't animate, but moving between the planet pages will.
    • The navigation must be same-origin, with no cross-origin redirects.
    • It must be a push, replace or traverse (back/forward) navigation. A push or replace must be started by the user interacting with the page, not by the browser's own UI such as the address bar or bookmarks. Reloads never animate.

    Customising it with JavaScript

    Two events let each page join in. In both, event.viewTransition is a ViewTransition object, or null if no transition will run:

    // Old page, just before it is replaced. Runs on the outgoing document.
window.addEventListener('pageswap', (event) => {
  if (event.viewTransition) {
    const destination = event.activation.entry.url; // where we're going
    event.viewTransition.types.add('drill-in');
  }
});

// New page, before its first frame is rendered.
window.addEventListener('pagereveal', (event) => {
  if (event.viewTransition) {
    const origin = navigation.activation.from?.url; // where we came from
    event.viewTransition.types.add('drill-in');
  }
});

    Add the pagereveal listener in a classic (not defer or module) script in the <head> so it's registered before the first frame. To avoid capturing a half-loaded page, you can also hold back rendering until the main content has been parsed:

    <link rel="expect" href="#main-content" blocking="render">

    Types can be declared in CSS too: @view-transition { navigation: auto; types: slide; }.

    Running the demo locally: some browsers treat pages opened straight from disk (file://) as unique origins, so cross-document transitions are most reliable over HTTP. From this folder, run python3 -m http.server and open http://localhost:8000/cross-document/. Current versions of Chrome run them from file:// as well.

    Best practices and gotchas

    • Treat it as an enhancement. If document.startViewTransition doesn't exist, run the update directly. Engines that only accept a callback throw a TypeError when given an options object, so wrap the { update, types } form in try/catch.
    • Respect reduced motion. Skip the transition when prefers-reduced-motion: reduce matches, or tone it down to a gentle cross-fade. For cross-document transitions, wrap @view-transition in a media query.
    • Keep the update callback fast. Rendering is paused while it runs, so the page looks frozen, and if it takes too long (about four seconds in Chrome) the transition is abandoned with a TimeoutError. Fetch data first, then start the transition.
    • Keep names unique. Two rendered elements with the same view-transition-name abort the transition with an InvalidStateError. Scope names to a type with :active-view-transition-type(), or add them just before the transition and remove them afterwards.
    • Name only what needs to move. Every named element is captured as its own snapshot and costs memory and time. Leave the rest to the root cross-fade.
    • Avoid stretched snapshots. Snapshots are scaled to the group's box. Use matching aspect ratios for images that morph and width: fit-content for text.
    • Name fixed and sticky UI. Named elements are painted above the root snapshot, so give a sticky header its own name or moving elements will slide over it.
    • Expect clicks to be swallowed. While a document-level transition runs, the pseudo-elements cover the page and pointer events go to the document element. Keep transitions short.
    • Handle the promises. ready and updateCallbackDone can reject. finished doesn't report an unhandled rejection, but the other two do unless you add a handler.
    • Manage focus and announcements. A transition is purely visual. Move focus to new content yourself and use live regions where content changes.
    • Debug with DevTools. View transition animations are ordinary animations on pseudo-elements, so you can slow them down, pause them and inspect them in the Animations panel, or list them with document.getAnimations().
